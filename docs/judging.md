# 판정과 통계

[← README](../README.md)

perfkit은 「기준 대비 얼마나 나아졌나」를 층·등급마다 판정합니다. 결정적 층(L0·L1)은 `diff` 그대로 보고, 회차 묶음(L2·L3-E·L3-D)은 **회차 단위 통계**로 봅니다. 측정 한 번의 숫자로는 판정하지 않습니다.

## 왜 등급을 나누나

같은 빌드라도 에뮬레이터와 실기기는 숫자의 뜻이 다릅니다. 에뮬레이터는 호스트 PC의 CPU·GPU를 빌려 쓰므로 절대값이 실기기와 무관하고, 발열·클럭·배터리는 아예 없습니다. 대신 같은 PC·같은 AVD에서 기준과 후보를 번갈아 돌리면 **상대 변화**는 볼 수 있습니다.

- 회차 메타의 `device_class`(`emulator`·`device`)가 등급입니다. 등급이 다른 회차를 한 비교에 섞으면 거부합니다(종료 코드 2).
- 에뮬레이터(L3-E)는 절대 기준 없이 변화만 보고, 통계로 개선이면 「실기기 확인 대기」(`needs_device_confirm`)를 붙입니다.
- 보고 HTML도 한 절에 한 층·한 등급만 둡니다.

## 비교 한 번의 흐름

1. 양쪽 회차 묶음을 모읍니다(SPEC: `session:`·`baseline:`·`run:`·폴더).
2. **관문에서 무효인 회차를 뺍니다**(`valid=false`, 또는 프로필 문턱 초과). 뺀 수와 이유를 남깁니다.
3. **일관성 검사**: 측정 코드(`probe_hash`)·시나리오·매니페스트(`manifest_sha`)·품질 설정(`quality_hash`)이 양쪽에서 다르면 비교를 무효로 표시합니다(종료 코드 3). 세이브·시드·기기 정의·OS 빌드가 다르면 경고합니다. 두 묶음의 측정 시각이 겹치지 않으면(교차가 아님) 경고하고 독립 비교로 봅니다.
4. 지표마다 통계 판정(아래) → 매니페스트 판정 규칙으로 항목 판정(통과·개선·경고·실패·확인 필요).
5. 비교 JSON(comparison 스키마)을 쓰고, `--report`면 HTML도 씁니다.

## 지표 하나의 통계 판정

| 단계 | 내용 |
|---|---|
| 효과 | Hodges-Lehmann 이동량, 기준 중앙값 대비 %. 중앙값 비율과 Cliff's δ도 싣습니다 |
| 구간 | 회차 단위 부트스트랩 백분위 95% 구간(기본 1만 회, 씨 고정 → 같은 입력이면 같은 구간) |
| 검정 | 쌍: Wilcoxon 부호순위, 독립: Mann-Whitney U(동점은 중간 순위, 작은 표본은 정확 분포) |
| 같음 | 구간 전체가 동등 범위 ±eq 안(먼저 봅니다). 0이 아닌 작은 이동이면 `minor_shift` 표시 |
| 다름 | 구간이 0을 품지 않고, p < 0.05이고, \|효과\| > 잡음 바닥. 방향은 매니페스트 `better`로 개선·악화 |
| 판단 보류 | 둘 다 아님, 회차 부족(기본 한쪽 3회 미만), 드리프트, 상태 섞임. 잡음 바닥이 있으면 필요한 라운드 수를 권고 |
| 판정 제외 | 프로필 `[compare."<층>"] exclude`에 든 지표. 값만 싣습니다 |

### 통계 용어 한 줄 풀이

- **Hodges-Lehmann 이동량**: 두 묶음 차이의 「대표값」. 쌍이면 라운드 쌍 차이들의 Walsh 평균(두 값씩 짝지은 평균) 중앙값, 독립이면 모든 b−a 조합의 중앙값입니다. 튀는 회차 하나에 덜 흔들립니다.
- **Cliff's δ**: 후보 값이 기준 값보다 큰 경우와 작은 경우의 비율 차(−1~1). 분포가 얼마나 겹치는지 봅니다.
- **부트스트랩 구간**: 회차를 다시 뽑기(복원 추출)를 1만 번 해서 효과의 95% 범위를 잡습니다. 분포 가정이 필요 없습니다.
- **Wilcoxon 부호순위 검정**: 쌍 차이의 부호와 크기 순위로 「차이가 0인가」를 봅니다(ABAB 쌍에 씀).
- **Mann-Whitney U 검정**: 두 묶음의 순위로 「같은 분포인가」를 봅니다(쌍이 없을 때).
- **Spearman 순위상관**: 라운드 번호와 쌍 차이가 같이 커지는지(드리프트) 봅니다.
- **CV(변동계수)**: 표준편차 ÷ 평균(%).

## ABAB 교차

기준(A)과 후보(B)를 한 번씩 모아 재면 그 사이의 기기 온도·호스트 부하·배경 작업 변화가 그대로 차이로 섞입니다. 그래서 `run abab`은 라운드마다 A·B를 한 번씩, 순서를 섞어 돌립니다(`Random(order_seed×1000 + 라운드)`, 같은 명령이면 같은 순서).

- 같은 라운드의 A·B가 한 **쌍**이 되고, 쌍 차이로 효과를 봅니다(`--pairing auto`가 라운드로 짝지음).
- 관문에서 무효인 라운드는 `compare`의 커밋·APK 파이프라인이 `--max-reruns`(기본 1)만큼 새 세션으로 다시 돌리고, 세션·라운드로 쌍을 짓습니다.
- 이미 잰 세션은 `compare --sessions S1,S2`로 다시 판정합니다(잡음 등급·판정 제외를 바꾼 뒤).

### 「다름」에 필요한 쌍 수

Wilcoxon 부호순위 검정은 쌍이 적으면 가장 극단적인 경우에도 p가 충분히 작아지지 않습니다. 쌍 5개면 최소 양측 p가 2/2^5 = 0.0625로 0.05에 못 미칩니다. 그래서 **쌍 5개 이하에서는 「다름」이 나오지 않습니다.** 6쌍 이상(최소 p = 0.03125)부터 가능하고, `compare --rounds`의 기본값이 6인 이유입니다. 잡음이 크면 그보다 많이 필요합니다(아래 MDE).

## A/A 잡음 바닥과 최소 탐지 변화

같은 빌드를 A/A로(두 쪽 다 같은 APK) 반복해 재면 「아무것도 안 바꿔도 나는 차이」를 알 수 있습니다.

```
python -m perfkit run abab --device emulator --a game.apk --b game.apk --rounds 6     # run_kind=aa
python -m perfkit noise aa --runs session:<A/A 세션> --target 5 --out noise.json
python -m perfkit baseline register --name main --runs <기준 SPEC> --noise-runs session:<A/A 세션>
```

- **σd**: A/A 회차에서 잰 지표별 잡음. σd = √2 · CV(%)(두 회차 차이의 흔들림).
- **MDE(최소 탐지 변화)**: n쌍으로 잡아낼 수 있는 가장 작은 변화. MDE(n) = 2.8 · σd / √n. 2.8은 양측 5% 유의수준과 검정력 80%의 z값 합(1.96 + 0.84)입니다.
- **필요한 라운드**: n = (2.8 · σd / 목표 MDE)². `noise aa --target 5`면 5% 변화를 잡는 데 필요한 n을 알려 줍니다.
- 잡음 바닥은 「다름」의 문턱이기도 합니다(|효과| > 잡음 바닥). 잡음 바닥이 없으면 잡음 등급별 기본 바닥을 씁니다: none 0 · low 1 · medium 3 · high 8 · very_high 12 · unknown 8(%).
- 매니페스트의 에뮬레이터 칸은 처음에 `pending_aa`입니다. A/A를 잰 뒤 프로필 `[overrides]`에서 잡음 등급을 채워야 L3-E 항목 판정이 나옵니다. 그전에는 통계 결과를 참고로만 싣습니다.

동등 범위(「같음」의 폭) 기본: none 1 · low 3 · medium 5 · high 10 · very_high 15 · unknown 10(%). 프로필 `[compare.equivalence_pct]`(등급별)나 `[compare."<층>".equivalence_pct]`(항목·지표별)로 바꿉니다.

## 같음·다름·판단 보류의 뜻

| 판정 | 뜻 | 할 일 |
|---|---|---|
| 같음 | 차이가 있더라도 동등 범위 안이라고 말할 수 있음 | 없음. `minor_shift`면 작은 이동이 있다는 표시 |
| 다름(개선) | 잡음을 넘는 변화가 있고 좋은 방향 | L3-E면 실기기에서 확인 |
| 다름(악화) | 잡음을 넘는 변화가 있고 나쁜 방향 | 원인 찾기(`bisect-step`) |
| 판단 보류 | 같다고도 다르다고도 말할 수 없음 | 권고된 라운드 수만큼 더 재거나, 상태 섞임·드리프트 원인을 없앰 |

「판단 보류」는 실패가 아닙니다. 데이터가 결론을 내기에 모자라다는 뜻입니다.

## 상태 섞임 검사

값이 몇 개의 이산 수준으로만 나뉘고(상대 0.5% 안을 한 수준으로 묶음) 같은 수준이 두 쪽에 함께 나오면, 「다름」을 판단 보류로 내립니다. 예를 들어 회차마다 장면 안 오브젝트 하나가 보이고 안 보이는 일이 있으면 정점 수가 두 값 사이를 오갑니다. 이때 두 쪽의 차이는 코드 변화가 아니라 「어느 상태가 몇 번 나왔나」의 비율 차이이므로 효과로 보지 않습니다. 이 경우는 게임 쪽 시나리오를 더 결정적으로 만들어야 합니다([Unity 쪽 약속](unity-contract.md#결정성)).

## 드리프트

쌍이 5개 이상이면 라운드 번호와 쌍 차이의 Spearman 순위상관(8개 이하는 정확 순열)을 봅니다. 유의하면(예: 라운드가 갈수록 B만 점점 느려짐 — 발열 누적, 저장 공간 증가) 같음·다름을 판단 보류로 내립니다.

## 호스트 유휴 관문

에뮬레이터 회차는 측정 전·측정 중 호스트 CPU 점유, 다른 에디터 프로세스 점유, logcat 재연결 수를 회차 메타 `host`에 남기고, `compare`가 프로필 `[compare."L3-E".gate]` 문턱으로 다시 검사합니다. 넘은 회차는 통계에서 빠집니다. 기본 문턱과 실기기 관문은 [수집 층](layers.md#관문).

## 호환 모드

측정 모드가 없는 빌드(예: 측정 코드를 넣기 전의 옛 기준 APK)는 `BEGIN` 줄이 없어 호환 모드로 돕니다. 이 회차는 기기 밖 지표(proc·meminfo·시작 시간)만 있습니다.

- 비교는 두 쪽에 다 있는 지표만 봅니다. 측정 코드·품질 설정 해시는 맞대지 않습니다.
- 측정 코드가 없는 쪽은 앱 상태가 달라(세이브·이동 잠금이 안 걸림) 런타임 지표를 맞댈 수 없을 때가 많습니다. 프로필 `[compare."<층>"] compat_items`를 두면 호환 모드에서는 그 항목만 비교합니다.
- 빌드 정보 JSON에서 측정 모드 여부 칸(`[build] probe_key`)이 아니면 보고 라벨에 「호환 모드」가 붙습니다.

## 기준선

```
python -m perfkit baseline register --name main --runs session:<세션> [--noise-runs session:<A/A>] [--l0 source.json] [--l1 l1.json] [--l2 play.l2.json]
python -m perfkit compare --base baseline:main --cand session:<새 세션>
```

- `perfkit/baseline@1`: 등급마다 회차 목록·유효 수·무효 회차·측정 코드·품질 설정 해시·환경·지표 요약·잡음 바닥, L0·L1 결과 참조. 같은 이름에 다른 등급을 더할 수 있습니다(같은 등급을 바꾸려면 `--force`).
- `--l2`: L2 결과(`editor play` 묶음)를 `editor.L2` 칸에 둡니다(회차 수·커밋·측정 코드 해시·시나리오·dirty). L2는 결정적 층이 아니라 따로 두고, `baseline:<이름>`을 비교 한쪽으로 쓸 때는 읽지 않습니다. L2 비교는 `perfkit diff <ref> <후보 L2>`.
- `--noise`를 주지 않으면 기준선의 잡음 바닥을 쓰고, 그것도 없으면 등급별 기본값을 씁니다.
