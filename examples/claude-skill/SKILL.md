# 성능 점검 (perf-check) — 틀

> 이 파일은 [unity-perfkit](https://github.com/cyKim0115/unity-perfkit)의 Claude Code 스킬 **틀**입니다. `<…>` 자리를 프로젝트 값으로 바꿔 `.claude/skills/perf-check/SKILL.md`로 둡니다. 붙이는 법은 같은 폴더 `README.md`.

호출 한 줄로 **점검 → 기준 대비 판정 → (증상이면) 가설 → 실험 브랜치 수정 → 재측정 → 판정 → 보고**까지 간다.
사용자 개입은 기기 연결·잠금 해제, 안전 범위 밖 수정 승인, 병합·푸시뿐이다.

| 구성 | 위치 |
|---|---|
| perfkit CLI | `<perfkit 클론>` — 저장소 루트에서 `python -m perfkit <명령>` |
| 점검 매니페스트 | perfkit `manifest/checks.json`(바꾸지 않음, 기준값 변경은 사용자 승인) |
| 프로젝트 프로필 | `<프로필 경로>/profile.toml`(기기·시나리오·관문·판정 제외·빌드 명령) |
| 결과 폴더 | `<결과 폴더>`(회차·기준선·비교·보고) |
| 게임 안 측정 모드 | `<측정 모드 코드 경로>`(브랜치 `<측정 브랜치>`) |
| 측정용 빌드 | `<빌드 명령>` 또는 직접 뽑은 APK |
| 고정 세이브 | `<프로필 경로>/saves/<이름>/` |

## 0. 먼저 지킬 것 (금지·관문)

### 금지

1. **등급을 섞지 않는다.** L3-E(에뮬레이터)와 L3-D(실기기)는 기준선·잡음 바닥·판정이 따로다. 다른 등급의 수치를 서로 비교하거나 한 표·한 그림에 넣지 않는다. 에뮬레이터 수치로 실기기 성능(목표 fps, 발열, GPU)을 말하지 않는다. L2(에디터 Play)도 별도 층이다. `perfkit compare`는 등급이 섞이면 종료 코드 2로 거부한다.
2. **에뮬레이터에는 절대 기준을 쓰지 않는다.** 같은 등급 기준 대비 변화만 본다. 에뮬레이터에서 개선으로 나온 항목은 「**실기기 확인 대기**」를 붙이고, 실기기 회차로 재현될 때만 뗀다.
3. **에뮬레이터에서 판정하지 않는 지표**(프로필 `[compare."L3-E"] exclude`)는 값만 싣는다. A/A에서 흔들림이 큰 지표, 호스트 GPU라 의미 없는 지표(GPU ms·하드웨어 카운터·발열·전력)가 여기다. 비교 이유에 「상태 섞임」이 보이면 장면 상태 문제라 개선·악화로 쓰지 않는다.
4. **1회 측정으로 판정하지 않는다.** 같은 빌드 A/A로 잡음 바닥을 재고, 기준·후보를 **ABAB 교차**로 잰다. 「다름」은 쌍 6개 이상일 때만 나온다. 다른 시각에 따로 잰 두 묶음은 진단용이다.
5. **「판단 보류」를 개선으로 쓰지 않는다.** perfkit 판정(같음·다름(개선·악화)·판단 보류)을 그대로 옮긴다. 동등 범위 안의 작은 이동은 같음이다.
6. **측정 코드·시나리오·세이브·판정 기준을 실험 브랜치에서 고치지 않는다.** 보호 대상: `<측정 모드 코드 경로>`, `<에디터 측정 도구 경로>`, 프로필·세이브, perfkit 저장소. 측정 코드가 바뀌면 `probe_hash`가 달라져 비교가 무효(종료 코드 3)다. 고칠 일이 생기면 멈추고 묻는다.
7. **에디터와 기기 측정을 동시에 돌리지 않는다.** 열린 에디터·배치 빌드는 adb 서버를 끊고 호스트 관문을 깬다. 한 회차에는 adb 하나만. 다른 작업이 호스트를 쓰는 중이면 기다린다.
8. **빌드는 `<빌드 명령>`으로만** 한다. 측정용 빌드 인자는 G6 고정값이다.
9. **Build Target·브랜치를 함부로 바꾸지 않는다.** `git clean -x`·경로 없는 `reset --hard`·`--amend`·`add -A`를 쓰지 않는다.
10. **결과·보고는 `<결과 폴더>`에만** 둔다. 게임 저장소에 결과를 커밋하지 않는다.
11. **병합·푸시·PR·보고 전송은 사용자 지시가 있을 때만.** 실험 브랜치는 로컬 커밋까지다.

### 단계 관문

**G1. 시작 전 상태** — `python -m perfkit config show`로 프로필·결과 폴더·adb가 맞는지. 다른 작업의 에디터·빌드·에뮬레이터가 돌면 기기 회차를 시작하지 않는다(L0는 가능). 실기기가 없으면(`device list`) L3-D는 「**기기 대기**」로 적고 그 단계만 건너뛴다.

**G2. 측정 브랜치** — 측정 모드가 있는 커밋인지 빌드 정보 JSON(`[run] build_info`)의 측정 모드 칸으로 확인한다. 없으면 호환 모드(기기 밖 지표만 비교)라고 보고에 적는다.

**G3. 에디터가 필요할 때** — `<에디터를 여는 절차>`. 남길 변경은 에디터를 닫기 전에 커밋한다. 닫은 뒤에야 빌드·기기 회차를 시작한다.

**G4. 에뮬레이터 회차 (L3-E)**
1. 에디터·빌드가 모두 끝났는지 확인.
2. `python -m perfkit device doctor --device <에뮬레이터 이름>` — adb 하나, AVD가 기대값과 같은지.
3. `python -m perfkit device host-gate --device <에뮬레이터 이름>` — 호스트 유휴 관문 pass.
4. `python -m perfkit run …`(once·abab·cold-start). 임대 도구가 없으면 `--no-lease`(또는 기기 정의 `lease = "none"`).
5. 무효 회차(`valid=false`)는 이유를 적는다. `compare`가 빼고 센다.

종료 코드: 0 끝 · 2 회차 실패 · 3 기기·설치·세이브 · 4 바쁜 호스트·남의 임대 · 5 AVD 설정 다름 · 6 스키마 오류. 4면 기다렸다 같은 명령을 다시, 5면 AVD를 고치지 말고 알린다.

**G5. 실기기 회차 (L3-D)** — 연결됐을 때만. `device doctor` → `device prep` → `device wait-cool`(회차 사이) → `run` → **`device restore`(반드시)**. 잠금·시간 초과는 사용자 호출.

**G6. 측정용 빌드** — 수치 회차는 `<릴리스 + 측정 모드 빌드 인자>`, 진단 회차(프로파일러 캡처)는 `<개발 빌드 + 측정 모드 인자>`. APK 경로를 외워 쓰지 않고 `<결과 폴더>/build-cache.json`이나 빌드 정보 JSON으로 찾는다. 빌드 도구가 없으면 APK를 직접 뽑아 `--base-apk`·`--cand-apk`로 준다.

**G7. 안전 범위와 승인** — 매니페스트 `fix_risk=safe` 중 `<안전 범위 목록>`만 실험 브랜치 `<실험 브랜치 접두어><주제>`에 로컬 커밋까지 한다. 그 밖(화질·동작이 바뀌는 것, 프로젝트·품질 설정, 패키지, 매니페스트·프로필 값, 보호 대상, 병합·푸시)은 먼저 묻는다. 한 실험 브랜치에는 **변경 하나**.

**G8. 보고** — 표·그림마다 층·등급을 적고 한 절에 한 등급만. 판정은 perfkit 값 그대로(「판단 보류(필요 라운드 N)」, L3-E 개선은 「실기기 확인 대기」, L3-D 없음은 「기기 대기」). 커밋·APK 해시·probe_hash·quality_hash·매니페스트 해시·회차 수·무효 수를 함께. HTML은 `perfkit report`(또는 `compare --report`).

## 1. 요청 흐름 고르기

| 사용자 말 | 흐름 |
|---|---|
| 「성능 점검해줘」 | (a) 점검만 |
| 「<APK·커밋> 대비 비교해줘」, 「이 커밋이 느려졌어?」 | (b) 기준 대비 비교 |
| 「<증상> 줄여줘」 | (c) 증상 줄이기 |

명령 이름·인자는 `python -m perfkit <명령> --help`와 perfkit `docs/commands.md`에 있는 것만 쓴다.

## 2. (a) 점검만 — L0 → L1 → (L2) → L3-E (→ L3-D)

기준은 등록된 기준선(`python -m perfkit baseline list`). 없으면 이번 결과를 첫 기준선으로 등록할지 묻는다.

1. **L0**: `python -m perfkit static --project <Unity 프로젝트>`. 에디터 점검 JSON이 있으면 `--editor <JSON>`. 에디터를 닫은 뒤에 돌린다(에디터가 다시 쓴 파일이 dirty로 잡힘).
2. **L1**: G6으로 빌드하거나 캐시 재사용 → `python -m perfkit build --apk <APK> [--log <빌드 로그>] [--layout <레이아웃 JSON>]`.
3. **L2**(에디터 측정 도구가 있을 때): 같은 조건 3회 → `python -m perfkit editor play <r1> <r2> <r3> --out <l2.json>` → 기준 L2와 `diff`. 같은 날 같은 에디터에서 잰 것끼리만.
4. **L3-E**: G4로 A/A(잡음 바닥이 없을 때) → `python -m perfkit run abab --device <에뮬레이터> --a <기준 APK> --b <이번 APK> --rounds 6 --scenario <시나리오> --session <이름>` → `python -m perfkit compare --runs session:<이름> --split arm --report`.
5. **L3-D**: 실기기가 있으면 G5로 같은 비교. 없으면 「기기 대기」.
6. **diff**: `python -m perfkit diff <기준> <이번>`(L0·L1, 결정적 층). 점검만의 판정 보고는 `diff <결과> --out <check.json>` → `report <check.json>`.
7. 보고(G8).

## 3. (b) 기준 대비 비교

1. 기준 풀기: APK는 그대로(`--base-apk`), 커밋·태그는 sha로(`--base-commit`). 버전만 받으면 빌드 정보 JSON에서 커밋을 찾고, 못 찾으면 묻는다(추측 금지).
2. 미리 보기: `python -m perfkit compare --base-commit <sha> --cand-commit <sha> --dry-run`.
3. 실행: `python -m perfkit compare --base-<commit|apk> … --cand-<commit|apk> … --device <에뮬레이터> --scenario <시나리오> --rounds 6 --report`. 빌드(캐시) → L1 → ABAB → 판정 → HTML. 빌드만 비교하면 `--no-run`. 오래 걸리므로 백그라운드로 돌리고 폴링하지 않는다.
4. 판정 읽기: 지표마다 같음·다름·판단 보류, 효과와 95% 구간, 필요 라운드. 판단 보류가 많으면 더 돌릴지 묻는다.
5. 실기기가 있으면 같은 비교를 따로 한 번 더(따로 보고 절).

악화 커밋 찾기는 `python -m perfkit bisect-step --base-apk <좋은 APK> --cand-head <클론>`을 `git bisect run`에 건다. 클론 HEAD를 바꾸므로 사용자 승인 뒤에만.

## 4. (c) 증상 줄이기 — 가설 → 실험 브랜치 → 변경 하나 → 재측정

1. **증상을 지표로**: 「줌아웃 끊김」 → FRM-01·02, GPU-04, GPU-07(원경 단계). 「메모리」 → MEM-03·04, CPU-04. 「로딩 김」 → AUX-04·BLD-10·BLD-11. 원인 위치는 L2 Frame Debugger·프로파일러 상위 마커로 찾는다.
2. **기준 측정**: 측정 브랜치 HEAD로 L0·L1과 L3-E A/A.
3. **가설 카드** `<결과 폴더>/hypotheses/<주제>.md`: 증상·지표·근거(항목 ID, 상위 마커)·변경 하나·예상 효과·검출 가능 여부(MDE)·안전 범위인지·되돌리는 법.
4. **안전 범위 판정**(G7). 밖이면 카드를 보여 주고 승인 전에는 고치지 않는다.
5. **실험 브랜치** `<실험 브랜치 접두어><주제>`를 측정 브랜치에서 만들고 변경 하나 → 컴파일 확인 → 그 파일만 시험 커밋.
6. **재측정**: `python -m perfkit compare --base-commit <측정 브랜치 HEAD> --cand-commit <실험 커밋> --device <에뮬레이터> --scenario <증상 시나리오> --rounds 6 --report` + L0·L1 diff.
7. **판정**: 목표 지표가 「다름·개선」이고 다른 지표에 「다름·악화」가 없으면 커밋 유지(「실기기 확인 대기」). 같음·판단 보류·악화면 패치로 보관(`git format-patch`)하고 실험 브랜치를 지운다(이번에 만든 미푸시 브랜치만).
8. 카드에 결과(비교 id·판정·보고 경로)를 채우고 보고(G8).

## 5. 결과 정리

- 색인: `python -m perfkit index rebuild` → `python -m perfkit index check`.
- 기준선: `python -m perfkit baseline register --name <이름> --runs session:<기준> --noise-runs session:<A/A> --l0 <source.json> --l1 <l1.json> [--l2 <l2.json>]`. 덮어쓰기(`--force`)는 승인.
